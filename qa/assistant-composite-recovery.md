# 单一备份窗口的组合恢复与回退演练

本机在彼此隔离的 PostgreSQL 16、Redis、删除日志和模拟效果账本上运行已打包候选。源与当前恢复实例使用 `combined-app-1795478827-guardian-eligibility`。旧版启动仅使用独立只读库及日志和账本副本。实际用户数据、供应商凭据、生产配置和签名资产均未参与。

## 一个备份点的四项撤销

在撤销前完成一次真实 PostgreSQL 归档，由同一文件恢复当前与旧版实验库。归档里有两个活跃分享、两条手动记忆、一份已批准监护同意和一个待审批动作，以及独立账号和其两个会话。

1. 源实例依次撤回一条公开分享、删除一条手动记忆、撤回监护同意并注销独立账号。四类事件 `SHARE`、`MEMORY`、`GUARD_REV` 和 `ACCOUNT` 写入同一独立日志。
2. 停止已验证身份的源 JVM。恢复库保留当前日志和账本，首次启动时关闭分享与记忆。旧链接和对照链接均不可读取，记忆读取和写入被拒绝。旧监护审批和两个被注销的设备会话仍受阻。
3. 在同一恢复库使用同一候选 JAR 打开分享和记忆。未撤销的分享和记忆恢复原内容，已撤销的链接和记忆保持不可访问。旧审批和注销会话继续被拒绝。

在三个阶段使用原有 v1 HTTP 请求字段重复同一个发送操作，每次并发发送六次且携带同一幂等键。运行和最终消息 ID 一致。未删除的会话仍有原来的两条消息，已用额度不变，保留额度为零。该组请求用于验证幂等和账本恢复。[本机 HTTP 结果](verify-results/composite-recovery-2026-11-24/runtime.log)

新库从零应用 170 项 Liquibase 变更。关闭和重新开启开关两次启动均运行零项新迁移。[迁移日志](verify-results/composite-recovery-2026-11-24/migrations.log)

## 旧版启动边界

用此前的 `combined-app-1795478827-catalog-portability` 尝试启动，首次连接即使用独立还原库的只读账号。核验该会话的事务只读属性，及建表、更新分享、删除记忆和写入运行的权限均未授予。关闭 Liquibase，使用独立 Redis 命名空间、源停止后的删除日志副本和模拟账本副本。

旧版拒绝新版删除日志并以退出码 1 结束，未到达服务就绪状态。端口无监听，八张表的行摘要与日志和账本副本散列均未变化。本机已验证的回退路径使用当前版本关闭再开启开关。[只读回退结果](verify-results/composite-recovery-2026-11-24/older-binary.log)

## 发布证据边界

这次演练验证本机隔离下的真实数据库迁移与备份恢复、服务停启、兼容 v1 请求、权限和用量账本。生产等价集群的压力和故障注入、各端签名包与旧客户端实机、生产数据库容量和恢复指标、获准供应商及市场运行证据仍待实测。任务 7.2 保持待验收。

## 还原后重新认证

普通设备会话行随数据库备份保存。恢复历史库时应用单独的认证切换步骤，在迁移完成且消费者流量仍暂停的还原库内清理 `assistant_session` 与 `assistant_organization_sso_session`。保留组织关联、账号、用户数据及独立权限日志。确认失效和重新认证后再开放访问。
